U2F → FIDO2: WebAuthn + CTAP

서버는 공개키만 갖고, 기기는 개인키를 안 내보내고, 브라우저는 도메인을 본다 — 피싱 내성의 실체는 이 세 조건의 조합

FIDO2는 WebAuthn(W3C 표준: 웹사이트 ↔ 브라우저 API)과 CTAP(FIDO Alliance 표준: 브라우저/OS ↔ 인증기 프로토콜)의 묶음이다. 사이트마다 다른 공개키 쌍을 만들어 등록하고, 로그인 때마다 서버가 준 1회용 챌린지에 개인키로 서명한다. 서명 안에 origin이 들어가고 브라우저가 RP ID를 검사하므로 가짜 도메인에서는 서명이 만들어지지 않는다.
RP 서버 — 공개키·credential ID·카운터만 보관 브라우저/OS (클라이언트) — origin·RP ID 검사, clientData 생성 인증기 — 개인키 생성·보관·서명. 보안키 또는 폰/PC의 보안 칩 UV — 사용자 확인 (PIN·생체). 인증기 안에서만 일어남

authData = rpIdHash ‖ flags(UP·UV·BE·BS) ‖ signCount ‖ (등록 시 credId·공개키). 사용자는 2·6 단계에서 인증기를 터치하거나 PIN·생체를 넣는다 — 그 결과는 flags 비트로만 서버에 간다.

왜 피싱이 안 되나 — 조건 세 개가 동시에

① 브라우저가 RP ID를 origin과 대조한다. WebAuthn L3 §5.11: "By default, Web Authentication requires that the RP ID be equal to the origin's effective domain, or a registrable domain suffix of the origin's effective domain." (L3가 추가한 related-origin은 RP가 .well-known으로 명시 opt-in해야 하므로 가짜 도메인에는 해당 없음.) 사용자가 https://examp1e.com(가짜)에 있으면 그 페이지는 rpId: "example.com"를 요청할 수 없다 — 브라우저가 §5.1.4 단계에서 SecurityError를 던진다. 가짜 사이트가 자기 도메인으로 요청하면 인증기에는 그 rpId로 만든 키가 없어서 서명할 것이 없다(§6.1: 인증기는 "the RP ID that the requested credential is scoped to exactly matches the RP ID supplied by the client"를 확인).
② 서명 안에 origin이 들어간다. 인증기가 서명하는 것은 authenticatorData ‖ SHA-256(clientDataJSON)이고(§6.3.3), clientDataJSON에는 origin과 challenge가 있다(§5.8.1). 그래서 어떤 경로로 서명을 얻더라도 서버가 origin을 대조하면 다른 도메인에서 만든 서명은 걸린다. AiTM 프록시가 중계해도 프록시의 origin이 박힌다.
③ 개인키가 기기 밖으로 안 나가고, 사용자는 비밀을 입력하지 않는다. 사용자가 입력하는 PIN·생체는 인증기 안에서 UV에만 쓰이고 네트워크로 가지 않는다(§4 User Verification: "locally authorizes the invocation"). 옮겨 적을 코드가 없으니 피싱 페이지가 받아 갈 것도 없다.

세 조건 중 하나만 있으면 안 된다. 공동인증서는 ③의 절반(개인키가 파일)과 ①②가 없어서 가짜 사이트에도 서명해 주고, TOTP는 ①②가 없어서 코드가 중계된다. 3장·2장에서 각각 다룬다.

U2F에서 FIDO2로 — 무엇이 바뀌었나

2014년 U2F는 2단계 전용이었다. 사용자가 아이디·패스워드를 넣은 뒤 보안키를 터치하면(UP만, UV 없음) 서버가 보관한 key handle로 키를 찾아 서명을 받았다. 키는 보안키가 발견(discover)할 수 없었고 — 서버가 credential ID를 먼저 줘야 했고 — 패스워드가 여전히 1차였다. 2019년 WebAuthn L1 + CTAP2가 두 가지를 더했다. discoverable credential(§4: "usable in authentication ceremonies where the Relying Party does not provide any credential IDs… navigator.credentials.get() with an empty allowCredentials") — 인증기가 rpId만 보고 자기 안의 키를 찾으므로 아이디 입력조차 필요 없다. 그리고 user verification — PIN·생체로 인증기 안에서 본인 확인을 하므로 "소유 + 지식/생체" 두 요소가 인증기 하나에 들어간다. 이 둘이 합쳐진 것이 패스워드 없는 1차 로그인이고, 2022년 그 자격증명에 붙은 이름이 패스키다.

서버에 남는 것 — 유출 시나리오

RP 서버 DB에는 사용자별로 credentialId, 공개키, signCount, 플래그(BE/BS), 선택적으로 attestation 정보가 남는다. 전부 유출돼도 공격자가 할 수 있는 건 없다 — 공개키로는 서명을 못 만든다. 패스워드 DB 유출이 곧 오프라인 크래킹인 것과 비교하면 이것이 FIDO의 두 번째 큰 효과다(첫 번째는 피싱 내성). 단, 유출된 credentialId·공개키로 "이 사람이 이 사이트 회원"임은 드러나고, 서버가 attestation을 저장했다면 인증기 모델도 드러난다.

Attestation — 선택 사항이고, 대부분 안 쓴다

등록 때 인증기는 "나는 제조사 X의 모델 Y이며 이 키는 내 안에서 만들어졌다"는 attestation을 제조사 인증서로 서명해 붙일 수 있다(§4: "verifiable evidence as to the origin of an authenticator"). RP는 attestation: "none" | "indirect" | "direct" | "enterprise"로 요청하고 기본값은 none(§5.4.7). 소비자 서비스는 거의 none — 어떤 기기든 받는다. 기업·정부는 direct로 "승인된 하드웨어 키만" 강제한다. Attestation이 없으면 서버는 그 키가 보안 칩 안에 있는지 소프트웨어 에뮬레이션인지 구분할 수 없다는 뜻이고, 그래서 "FIDO2 = 하드웨어 보안"은 attestation을 요구할 때만 맞는 말이다.

흔한 오해

"지문이 서버로 간다." 안 간다. 생체는 인증기 안의 UV에만 쓰이고, 서버는 "UV 비트 = 1"만 본다. 생체 템플릿은 기기 밖으로 나갈 이유가 없다.
"FIDO2 = 패스키." 패스키는 FIDO2 자격증명 중 discoverable한 것에 붙은 이름이다. U2F식 2단계 보안키도 FIDO2(CTAP2)로 동작하지만 패스키라 부르지 않는다. 4장 둘째 페이지.
"보안키를 사야 FIDO." 폰·노트북의 보안 칩(Secure Enclave, TPM)이 플랫폼 인증기로 동작한다. 보안키는 "기기에 묶인(device-bound)" 쪽의 선택지일 뿐.
"피싱 내성이 있으니 MFA다." 반대다. 피싱 내성과 요소 수는 별개(0장). UV 없는 보안키 터치는 1요소이면서 피싱 내성이고, 패스워드+TOTP는 2요소이면서 피싱 취약이다.

내 연구와의 접점

FIDO2가 없애는 것은 정확히 내 논문의 대상 — "사람이 고른 비밀"이다. 키는 난수, 사이트마다 다르고, 서버엔 공개키만. 전이 예측(PPB)도 서비스별 예측 가능성(PSI)도 정의상 사라진다. 남는 질문은 두 가지. 첫째, 이 자격증명을 등록·복구하는 절차에 패스워드가 남아 있는가(거의 항상 남아 있다). 둘째, 어떤 서비스가 실제로 도입했는가(Top-100K 중 스캔 가능 사이트의 11.3%, 9,397개). 내 논문이 재는 층은 그 89%와, 11%의 복구 경로다.
