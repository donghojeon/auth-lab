클라이언트 인증서·스마트카드·SSH 키

같은 공개키 인증인데 키가 파일에 있느냐 칩에 있느냐로 위협 모델이 갈린다. 그리고 셋 모두 "키를 나눠 주고 거두는 일"에서 무너진다

클라이언트 인증서(mTLS·EAP-TLS)는 사용자가 TLS 핸드셰이크 안에서 인증서로 서명해 서버에 자신을 증명하는 방식, 스마트카드(PIV·CAC)는 그 개인키를 꺼낼 수 없는 칩에 넣고 PIN으로 활성화하는 방식, SSH 키는 CA 없이 공개키를 서버의 허용 목록에 직접 넣는 방식이다. 셋의 공통 골격은 앞 페이지의 챌린지-응답이고, 차이는 두 축 — 키가 어디 있나(파일 / 칩)와 공개키를 누가 보증하나(CA / 허용 목록 / 아무도).

위쪽 두 칸은 PKI(앞 페이지 ②가 있음), 아래 두 칸은 허용 목록(① 만). 왼쪽은 키가 복사되는 세계, 오른쪽은 사용만 되는 세계. 한국의 공동인증서는 왼쪽 위에서 출발해 보안토큰이면 오른쪽 위로 간다. FIDO는 오른쪽 아래. 각 칸의 위협 모델이 다르니 "공개키 인증"이라는 한 단어로 묶으면 비교가 안 된다.

클라이언트 인증서: TLS 핸드셰이크 안의 서명

서버가 CertificateRequest를 보내면 클라이언트는 인증서와 함께 CertificateVerify — 지금까지의 핸드셰이크 전체 해시(transcript)에 대한 서명 — 를 보낸다(RFC 8446 §4.4.3). 서명 대상에 핸드셰이크가 통째로 들어가므로 중계 공격이 성립하지 않는다 — 가짜 서버는 자기 핸드셰이크에 대한 서명을 진짜 서버에 가져가 쓸 수 없다. 이것이 앞 페이지에서 말한 "문맥"의 교과서적 구현이고, 63B-4 §3.2.5는 이를 피싱 내성의 예로 직접 든다: "Personal identity verification (PIV) and common access card (CAC) cards, which use client-authenticated TLS, provide phishing resistance through channel binding." 같은 구조가 Wi-Fi 802.1X의 EAP-TLS, VPN, 기업 내부 API의 mTLS에 쓰인다.

그런데 사용자용 클라이언트 인증서는 웹에서 거의 사라졌다. 이유는 암호가 아니라 운용이다: 브라우저마다 다른 가져오기 UI, 기기마다 설치·갱신, 분실 시 폐지 전파, 그리고 키가 OS 키 저장소에 파일로 있어 단말 감염에 그대로 노출된다는 점. 기업은 이 문제를 "기기 인증서를 MDM이 자동 배포"로 풀었고(사용자가 아니라 기기를 인증), 사용자 인증은 IdP + MFA/패스키로 넘겼다. 즉 클라이언트 인증서는 사람 인증에서 기기 인증으로 역할이 옮겨 갔다.

스마트카드: 키를 꺼낼 수 없게 만들기

미국 연방 PIV(FIPS 201-3)와 국방부 CAC는 개인키를 카드 안에서 만들고 꺼내지 못하게 한 설계다. FIPS 201-3 §4.2.2.1: "This key SHALL be generated on the PIV Card. The PIV Card SHALL NOT permit exportation of the PIV authentication key." PIN은 카드를 활성화하는 지식 요소이고, 활성화된 카드는 연산마다 PIN을 다시 묻지 않아도 된다(같은 조항, MAY). 일반 비접촉(NFC) 인터페이스로는 인증 키 연산을 막고, 보안 채널(virtual contact interface)로만 허용할 수 있다. 그래서 63B-4의 multi-factor cryptographic authenticator(소유 = 카드, 지식 = PIN)이고 AAL3의 "non-exportable private key" 조건을 만족한다. 카드를 훔쳐도 PIN 시도 제한에 걸리고(추정: 구체 횟수는 카드·기관 정책별), PIN을 알아도 카드가 없으면 소용없다. FIDO 보안키도 같은 원리(비반출 키 + 로컬 활성화)를 쓴다 — YubiKey 한 개에 PIV와 FIDO2가 같은 물건 위의 다른 프로토콜로 들어 있다. 차이는 셋이다: PKI(CA 체인·인증서) 유무, 서비스별 키 여부, 그리고 서명이 무엇에 묶이나(TLS 채널 vs origin).

Windows Hello for Business는 같은 원리를 카드 대신 노트북의 TPM으로 구현한다. 키는 TPM이 있으면 TPM 안에서(없으면 소프트웨어 키로 — MS 문서: "device-bound key (hardware or software)") 생성되고 PIN·생체는 그 키를 여는 로컬 잠금 해제다. AAL3 조건(비반출)은 TPM 키일 때만 선다. Entra ID에는 언제나 이 키로 인증하고("always uses the key, not a certificate"), 온프레미스 AD 인증 방식만 세 가지 신뢰 유형으로 갈린다 — cloud Kerberos trust(Entra가 TGT를 발급, MS 권장), key trust(장치 바인딩 키로 직접), certificate trust(사내 CA가 사용자에게 인증서 발급, 앞 칸의 "하드웨어 인증서"). Windows Hello는 웹 사이트에 대해서는 FIDO2/WebAuthn 플랫폼 인증기로도 동작하지만, Entra·AD 로그인 자체는 FIDO2 프로토콜이 아니다.

스마트카드의 약점은 카드가 아니라 발급 창구다. 카드를 누구에게 주는지(신원 확인), 분실 신고와 폐지가 얼마나 빨리 전파되는지, PIN 초기화 절차가 사회공학에 얼마나 약한지. 0장의 "등록·복구가 가장 약한 고리"가 여기서도 그대로다.

SSH 키: CA 없는 공개키 인증의 성공 사례

SSH publickey 인증(RFC 4252 §7)은 클라이언트가 (세션 ID ‖ 사용자명 ‖ 서비스 ‖ 공개키) 를 개인키로 서명해 보내고, 서버는 그 공개키가 authorized_keys에 있는지 보고 서명을 검증한다. 세션 ID가 서명 대상에 들어가므로 중계가 안 된다. CA가 없다 — 공개키를 허용 목록에 누가 넣느냐가 전부고, 그래서 FIDO의 "서비스별 공개키 등록"과 구조가 같다. 호스트(서버) 쪽 인증은 처음 접속 때 본 키를 믿는 TOFU(trust on first use)라, 첫 접속(또는 키 변경 경고를 무시할 때) 서버 사칭을 막지 못한다. 그때도 사용자 키 인증 자체는 세션 ID가 달라 중계되지 않지만, 가짜 서버가 세션 내용을 보고 포워딩된 에이전트를 악용할 수 있다.

잘 되는 이유와 안 되는 이유가 같다. 키 생성·등록이 명령 한 줄이라 개발자 세계 전체가 쓰지만, 그 결과 키가 어디 몇 개 있는지 아무도 모른다. 퇴사자의 키가 서버에 남고, passphrase 없는 개인키가 노트북·CI 서버·도커 이미지에 복사돼 있고, 에이전트 포워딩은 침해된 중간 서버에서 내 키를 빌려 쓰게 한다. 2015년 Ben Cox가 GitHub 사용자 공개 SSH 키 약 137만 개를 전수 조사했을 때, 256·512비트 RSA 키가 남아 있었고 2006~2008년 Debian OpenSSL 난수 버그(키 공간 약 3.2만 개)로 만든 키가 대량으로 — 일부는 큰 프로젝트의 커밋 권한과 함께 — 살아 있었다. GitHub는 신고 후 2015년 5~6월에 해당 키를 일괄 폐기했다. "아무도 키를 추적하지 않는다"의 공개 증거다. 대응은 두 갈래다 — OpenSSH 인증서(사내 SSH CA가 ssh-keygen -s로 짧은 유효기간의 인증서를 발급, 왼쪽 위 칸으로 이동)와 FIDO 키(OpenSSH 8.2, 2020-02부터 ed25519-sk·ecdsa-sk 키 유형, 오른쪽 아래 칸으로 이동).

흔한 오해

"SSH 키는 패스워드보다 무조건 안전." 서버 쪽(추측·유출)은 그렇다. 단말 쪽은 passphrase 없는 키 파일이 곧 패스워드 평문과 같다 — 복사 한 번이면 끝. 에이전트 포워딩까지 켜면 침해된 서버가 내 키로 다른 서버에 들어간다.
"스마트카드는 구식, 패스키가 신식." 같은 설계(비반출 키 + 로컬 PIN)의 두 세대다. 차이는 PKI 유무와 "서비스마다 다른 키"뿐이고, YubiKey 한 개에 둘 다 들어 있다.
"클라이언트 인증서는 사라졌다." 사람 인증에서는 그렇지만 기기 인증(MDM 배포 인증서, mTLS 서비스 간 인증, EAP-TLS)에서는 표준이다. 사라진 건 "사람이 인증서를 관리하는" 모델이다.
"TPM이 있으니 노트북이 곧 보안키." TPM은 키를 지키지만 PIN 입력은 OS 위에서 받는다. OS가 감염되면 PIN 입력 순간 키를 "사용"당한다. 보안키의 물리 터치가 그 틈을 좁히는 장치다.

내 연구와의 접점

이 페이지의 왼쪽 열(파일 키)에서 "잠금 패스워드"는 내 연구 대상이 그대로 돌아오는 자리다. SSH passphrase·.p12 비밀번호·공동인증서 비밀번호는 전부 사람이 고른 문자열이고, 파일이 유출되면 오프라인 추측이 시작된다 — 그런데 이 패스워드들은 로그인 패스워드와 달리 차단 목록·시도 제한·유출 대조가 전혀 없다. 사용자가 로그인 패스워드를 재사용해 키 파일을 잠근다면(추정: 측정 연구 미확인) PentaPassBreaker의 전이 예측이 그대로 적용된다. 오른쪽 열(칩 키)로 옮기면 그 변수가 사라진다. 패스워드 이후를 묻는 질문의 답이 "공개키냐 아니냐"가 아니라 "키가 파일이냐 칩이냐"인 이유.
