Kerberos 인증 흐름

Active Directory가 직원을 인증하는 방식 — 패스워드는 네트워크에 한 번도 흐르지 않고, 대신 "티켓"이 돈다

Kerberos는 신뢰받는 제3자(KDC)가 발급하는 대칭키 암호화 티켓으로 클라이언트와 서비스가 서로를 인증하는 네트워크 인증 프로토콜이다 (RFC 4120). Active Directory 도메인 로그인의 기본 프로토콜.
Kuser — 사용자 패스워드에서 만든 키 Ktgs — KDC만 아는 키 (AD의 krbtgt 계정) Ksvc — 서비스 서버의 키 (서비스 계정 패스워드) SK — 그 자리에서 만든 1회용 세션 키

표기: { 내용 }K = 내용을 키 K로 암호화. 색은 "누가 열 수 있는 키인가"를 뜻함.

단계별로

1

AS-REQ — "나 jdh, 로그인할게"

PC가 패스워드로 Kuser를 만들어 현재 시각을 암호화해 보냄(pre-authentication). 패스워드 자체는 보내지 않음. KDC는 자기가 가진 jdh의 Kuser로 풀어서 시각이 맞으면 "패스워드를 아는 사람"으로 인정.

2

AS-REP — 세션키 + TGT

두 덩어리. (a) 세션키 SK1을 Kuser로 잠가서 — PC만 열 수 있음. (b) TGT(Ticket Granting Ticket): "jdh, SK1, 소속 그룹(PAC), 10시간 유효"를 Ktgs로 잠근 것 — PC는 못 열고 들고만 다님. 여기서 패스워드 역할 끝. 이후 10시간은 TGT가 패스워드를 대신함.

3

TGS-REQ — "파일서버 티켓 주세요"

TGT + authenticator({jdh, 현재시각}을 SK1로 암호화) + 원하는 서비스 이름. KDC는 TGT를 Ktgs로 열어 SK1을 꺼내고, 그 SK1로 authenticator가 풀리면 "TGT의 진짜 주인"임을 확인. 시각이 5분 이상 어긋나면 거부(재전송 방지).

4

TGS-REP — 서비스 티켓

또 두 덩어리. (a) 새 세션키 SK2를 SK1로 잠가서. (b) 서비스 티켓: "jdh, SK2, 그룹, 만료"를 Ksvc(파일서버의 키)로 잠근 것. PC도 KDC 이외 누구도 못 여는 봉투.

5

AP-REQ — 파일서버에 제시

서비스 티켓 + authenticator({jdh, 시각}을 SK2로). 파일서버는 자기 Ksvc로 티켓을 열어 SK2와 그룹 정보를 얻고, SK2로 authenticator가 풀리면 접속 허용. KDC에 물어보지 않음 — 티켓 자체가 증거.

6

AP-REP — 서버도 자기 증명 (선택)

서버가 authenticator에 있던 클라이언트의 시각(ctime·cusec)을 그대로 SK2로 암호화해 돌려줌(v4의 "시각+1"은 v5에서 불필요, RFC 4120 §3.2.5). SK2를 아는 건 진짜 파일서버뿐이므로 PC도 서버가 가짜가 아님을 확인(상호 인증).

"10시간"과 "5분"은 RFC가 아니라 Windows 기본값(TGT 수명 10시간, 허용 시각 차 5분). RFC 4120은 시각 차 한계를 예시로만 5분을 든다(§3.2.3).

왜 안전한가 — 설계 포인트 4개

패스워드가 네트워크에 안 흐른다. 1단계에서 패스워드로 만든 키로 "시각"만 암호화. 도청자는 암호문만 봄. (단, 이 암호문을 오프라인에서 사전 공격할 수는 있음 → 아래 "공격" 참고)
티켓은 받는 쪽만 열 수 있다. TGT는 KDC 키, 서비스 티켓은 서비스 키로 잠김. 클라이언트는 운반만 하므로 내용(그룹·만료)을 위조 못 함.
authenticator = "지금 이 순간의 나". 티켓을 훔쳐도 세션키 없이는 authenticator를 못 만들고, 시각 검사로 녹음 재생(replay)도 막음.
인가 정보가 티켓에 실려 간다. PAC(그룹 SID 목록)이 티켓 안에 있어, 서비스는 KDC에 다시 묻지 않고 권한을 결정. Entra/Okta의 SAML·OIDC 토큰이 하는 일과 같음.

실제 쓰이는 곳 — IdP 토큰과의 대응

Active Directory 도메인에 가입한 모든 Windows PC·서버·앱(파일 공유, SQL Server, IIS 통합 인증 등)이 기본으로 쓴다. 클라우드 IdP(Entra ID·Okta)의 SSO는 암호 방식만 다르고 구조는 같다.

Kerberos (AD, 사내)Entra ID / Okta (클라우드 SSO)역할
Kuser 로그인 (AS 교환)IdP 로그인 페이지 (패스워드 / MFA / 패스키)딱 한 번 본인 확인
TGT (10시간)IdP 세션 쿠키재로그인 없이 티켓을 더 받을 권리
서비스 티켓 (Ksvc로 암호화)SAML assertion / OIDC ID token (IdP 개인키로 서명)특정 앱 하나용 증명서
PAC (그룹 SID)토큰 claims (groups, roles)권한 전달
Ksvc를 미리 공유IdP 공개키를 앱에 미리 등록 (federation)신뢰 관계 사전 설정

차이는 "대칭키를 미리 나눠 갖는가(Kerberos) vs 공개키 서명을 믿는가(SAML/OIDC)"뿐이고, 구조는 같다. 그래서 AD→Entra 이전이 자연스러웠음.

흔한 오해

"Kerberos는 패스워드를 안 쓴다." 안 보내는 것이지 안 쓰는 것이 아니다. 사용자 키·서비스 키·krbtgt 키 전부 패스워드에서 나온다.
"티켓만 훔치면 로그인된다." 티켓만으로는 authenticator를 못 만든다. 세션키도 함께 있어야 한다 (그래서 실전 공격은 티켓+세션키를 메모리에서 함께 뽑는다).
"AD 로그인 = NTLM." 도메인 환경 기본은 Kerberos. NTLM은 이름 대신 IP로 접속하거나 Kerberos를 못 쓸 때의 폴백이며, 패스워드 해시 기반 챌린지-응답이라 더 약하다.
"PAC는 Kerberos 표준이다." PAC의 형식과 내용(그룹 SID)은 Microsoft 확장(MS-PAC). RFC 4120은 티켓에 authorization-data 필드를 두지만(§5.3) 용도를 "티켓 사용 제한"으로만 정의하고 내용은 정하지 않는다.

내 연구와의 접점 — 그래도 패스워드가 문제인 지점

AS-REP Roasting / pre-auth 오프라인 크래킹 — pre-auth가 꺼진 계정은 AS-REP을 그냥 요청해 2단계 암호문을 오프라인에서 패스워드 추측(AS-REP roasting). pre-auth가 켜진 계정도 1단계 암호문을 도청하면 같은 방식으로 추측 가능. 둘 다 Kuser가 패스워드에서 유래하기 때문이고, 약한 패스워드면 뚫림.
Kerberoasting — 4단계 서비스 티켓은 서비스 계정의 패스워드로 잠겨 있음. 도메인 사용자는 누구나 아무 서비스 티켓을 요청할 수 있으므로, 받아서 오프라인으로 서비스 계정 패스워드를 추측. AD 환경 실전 공격 1순위 — 결국 패스워드 강도 문제.
Golden Ticket — Ktgs(krbtgt 패스워드 해시)가 유출되면 공격자가 TGT를 마음대로 위조. 도메인 전체 함락.
요지: Kerberos는 패스워드를 "안 보내는" 것이지 "안 쓰는" 것이 아니다. 사용자 키·서비스 키·krbtgt 키 전부 패스워드에서 나오고, 가장 성공률 높은 AD 공격들이 그 패스워드를 오프라인에서 추측하는 것. 티켓 구조가 아무리 정교해도 바닥은 패스워드 — 본 논문이 다루는 층.
