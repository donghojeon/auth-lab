서버 저장: 해시·솔트·KDF

서버는 패스워드를 알 필요가 없다. "맞는지 확인"만 하면 된다. 그 확인을 유출된 DB로는 못 하게 만드는 기술이 40년에 걸쳐 쌓인 것이 이 페이지

패스워드 저장은 비밀 p를 그대로 두지 않고 H(salt, p)만 두고, 로그인 때 다시 계산해 비교하는 것이다. 공격자가 DB를 통째로 가져가도 p를 되찾는 데 "추측 한 번당 H 한 번"의 비용을 치르게 하는 것이 목적. 솔트는 추측을 계정마다 따로 하게 만들고, KDF(키 유도 함수)는 추측 한 번을 비싸게 만든다. 이 둘이 없으면 유출 = 평문이다.

위: 등록·로그인은 같은 함수를 두 번 부른다. 아래: 유출 뒤 공격자도 같은 함수를 부르는데, 추측 한 번당 한 번씩이다. 그래서 함수가 느릴수록, 메모리를 많이 먹을수록 공격자의 초당 추측이 줄어든다. 솔트는 "모든 계정을 동시에 추측"을 막아 계정 수만큼 비용을 곱한다.

네 세대: 평문 → 해시 → 솔트 해시 → 느린 KDF

Morris와 Thompson의 1979년 논문이 이미 세 번째 세대까지 다 말했다. UNIX crypt(3)는 DES를 25회 반복하고 12비트 솔트를 붙였다. 솔트의 역할을 그들은 정확히 썼다: 같은 패스워드를 쓰는 두 사용자의 저장값이 달라지고, 미리 계산한 표를 쓸 수 없게 된다. 그 뒤 40년은 "25회 반복"이 하드웨어 속도를 따라잡지 못한 역사다.

KDF 고르기: 무엇이 "느리다"를 만드나

느림에는 두 종류가 있다. 반복(PBKDF2, bcrypt)은 CPU 시간을 쓰고, 메모리 경직성(scrypt, Argon2)은 RAM까지 쓴다. GPU·ASIC은 연산은 수천 배 병렬화하지만 코어당 메모리는 늘리기 어렵기 때문에, 메모리를 먹는 함수는 공격자의 "하드웨어 이점"을 깎는다. 그래서 2015년 Password Hashing Competition이 Argon2를 뽑았고, OWASP는 Argon2id를 1순위로 둔다.

OWASP가 다섯 Argon2 설정을 "동급"으로 두는 이유는 메모리와 CPU를 맞바꾼 것뿐이기 때문이다. 어떤 설정이든 핵심은 서버가 감당하는 최대치로 두는 것이다. 63B-4의 표현: "The chosen cost factor SHOULD be as high as practical without negatively impacting verifier performance." RFC 9106과 OWASP 어느 쪽도 이 값의 근거로 공격 하드웨어의 메모리 크기를 들지 않는다. RFC 9106은 64 MiB를 "If much less memory is available"일 때의 둘째 권장(§4, §7.4 "memory-constrained environments")으로 두고, 첫째 권장 2 GiB에 대해서는 "maximizes adversarial costs on dedicated brute-force hardware"라고 쓴다.

cost·m·t·p 같은 파라미터는 함수 입력의 일부라 바꾸면 같은 패스워드도 전혀 다른 해시가 된다(Argon2는 파라미터를 H₀에 넣는다). 그래서 DB 행에 알고리즘·파라미터를 함께 두고(도식 맨 오른쪽), 설정을 올릴 때는 다음 로그인에서 받은 평문으로 다시 해시하는 것이 일반적이다.

직접 돌려 보기 (9장 실습 랩). 위 표의 "느림"을 손으로 확인하는 세 페이지다. 순서대로 보면 이 절의 흐름과 같다.
  • HMAC-SHA256 해부도: PBKDF2의 반복 한 번이 바이트 단위로 무엇을 하는지, 왜 반복 1회가 압축 2회인지.
  • 메모리 하드 함수 실험실: 반복만 하는 함수와 메모리를 채우고 되읽는 함수의 차이, 공격자 칩 면적으로 본 비용.
  • Argon2 메모리 행렬: lane·slice 행렬이 채워지는 순서와 d·i·id가 참조 블록을 고르는 방식.

얼마나 느려야 하나: 오프라인 크래킹의 경제학

"느린 KDF는 얼마나 느려야 하나"에 모델로 답한 것이 Blocki·Harsha·Zhou(IEEE S&P 2018)다. 합리적 공격자는 다음 추측의 기대 수익 pi·v(pi = i번째 추측이 맞을 확률, v = 깬 계정 하나의 가치)가 그 추측의 기대 비용 k·(1 − λi−1)보다 큰 동안 추측한다. 이미 맞힌 계정에는 더 계산하지 않으므로 비용에 "아직 못 깬 확률"이 곱해진다. 정확히는 총이익을 최대로 만드는 멈춤 순위를 고른다. 저자들은 Yahoo 약 7천만 계정의 빈도표에 CDF-Zipf 법칙 λt = y·tr(상위 t개 추측의 누적 성공률)을 피팅해 y = 0.0211, r = 0.2166을 얻었다. 이 빈도표는 유출본이 아니라 Bonneau가 Yahoo의 협조로 수집했고, 2016년 Blocki·Datta·Bonneau가 차분 프라이버시를 걸어 공개한 것이다(추측 모델). Zipf 분포에서는 임계값 T(y, r, a)가 있어서 v/k ≥ T이면 끝까지 다 깨는 것이 최적 전략이 된다(정리 1). a는 수확 체감 지수로, 1이면 계정을 많이 깰수록 값이 떨어지는 효과가 없다는 뜻이다. Yahoo 피팅으로 T(y, r, 1) ≈ 2.25×107, a = 0.8이면 2.69×107이다.

여기에 공개된 해시 설정을 넣으면, 계정 가치를 가장 낮게 잡고(v = $0.28, 수확 체감 a = 0.8) 계산해도 Dropbox(bcrypt cost 8)·Ashley Madison(bcrypt cost 12)·LastPass(2015년 침해 당시 PBKDF2-SHA256 10만 회, 2017년 NIST 최소 1만 회의 10배)는 비밀번호 분포가 Yahoo·RockYou 수준이라면 임계값을 넘는다. Yahoo는 bcrypt 반복 수가 공개되지 않아 τ별로 예측했다. 이 LastPass 값은 위 표의 2022년 금고 100,100회와 다른 대상이다. Zipf 가정을 빼고 관측 분포만으로 계산해도 Yahoo는 최소 51%가 깨진다(v/k = 7×108, a = 1). Yahoo가 PBKDF2·bcrypt로 100% 크랙을 피하려면 τ = 226(약 7초)까지 올려야 하고($30 공격자, a = 1), 20% 아래로 내리려면 τ ≈ 232(400초 이상)이 필요하다($4 공격자, Zipf 가정). 반복형 함수도 k를 올릴 수는 있지만 로그인 지연에 비례해서만 오르기 때문이다.

메모리 하드 함수는 비용 식이 다르다. 논문은 PBKDF2·bcrypt를 k = τ·CH, 메모리 하드 함수를 k = τ·CH + τ²·Cmem로 둔다. τ 단계 동안 τ에 비례하는 메모리를 쥐고 있어야 해서 면적×시간이 τ²로 오르기 때문이다. 그래서 로그인 지연을 1초까지 늘리지 않고도 크랙 비율을 22.2% 아래로 낮출 수 있다고 계산한다(모델과 무관한 상한, v/k = 104 기준). 0.1초(τ = 220) 메모리 하드 함수만으로도 $30 공격자가 전부를 깨지는 않는다. τ²가 생기는 과정은 메모리 하드 실험실에서 볼 수 있다.

읽을 때 주의. 실제로 해시를 깬 실험이 아니라 모델 기반 계산이다. 결과는 Zipf 피팅, v(암시장 가격), CH 추정에 따라 움직인다. CH는 2013년 비트코인 채굴 보상을 해시 수로 나눠 역산한 SHA-256 1회 단가(≈ $7×10−15)이고, 공격자가 PBKDF2·bcrypt 전용 ASIC을 만든다고 가정한 값이다. Zipf는 입증이 아니라 피팅이다. τ²도 이상적인 경우이고, Argon2i는 Alwen–Blocki 공격(CRYPTO 2016)으로 그보다 싸게 계산된다. 논문도 §8 Discussion에서 메모리 하드 함수를 써도 오프라인 공격의 피해는 여전히 클 수 있다고 말하며, 분산 해싱·MFA·허니 계정을 함께 권한다.

NIST SP 800-63B-4 §3.1.1.2가 저장에 대해 요구하는 것

  • SHALL "store passwords in a form that is resistant to offline attacks. Passwords SHALL be salted and hashed using a suitable password hashing scheme."
  • SHALL 솔트 ≥ 32비트, 충돌 최소화되게 선택. (32비트는 하한이고 실제 구현은 128비트가 흔함 — Argon2 RFC 권고 128비트.)
  • SHOULD SP 800-132 또는 후속 지침의 승인된 해싱 스킴 사용. SP 800-132에는 지금 PBKDF2만 있고, 63B-4 본문은 메모리 하드 함수를 언급하지 않는다. 63B-3(2017)에는 "A memory-hard function SHOULD be used because it increases the cost of an attack"과 PBKDF2 "typically at least 10,000 iterations"가 있었지만 63B-4에서 빠졌다. NIST는 2023년 SP 800-132를 개정해 메모리 하드 함수를 추가로 승인하기로 결정했다(2026-10 확인 기준 초안 미공개). 63B-4에서 빠진 이유가 FIPS 승인 체계 때문이라는 해석은 문서 근거가 없는 추정이다.
  • SHOULD "perform an additional iteration of a keyed hashing or encryption operation using a secret key known only to the verifier" — 이것이 pepper. 그 키는 SHALL 해시와 분리 저장, SHOULD HSM·TEE·TPM 같은 하드웨어 보호 영역 안.
  • SHALL 패스워드 전체를 받아 전체를 검증 (잘라내기 금지 — bcrypt 72바이트가 걸리는 지점).

pepper의 의미를 정확히 하면: DB만 유출되고 pepper는 안 나갔다면 공격자는 추측 자체를 못 한다(비교 대상이 없음). KDF가 "추측을 비싸게"라면 pepper는 "추측을 불가능하게"다. 대신 pepper가 같이 나가면 아무것도 아니므로, 분리 저장이 조건이 아니라 정의다. OWASP도 "alone, it provides no additional secure characteristics"라고 못 박는다.

비밀 값을 섞자는 생각은 Manber(1996)의 "secret salt"까지 거슬러 간다. 다만 그의 방식은 짧은 비밀 솔트를 아무 데도 저장하지 않고, 검증할 때 서버도 가능한 값을 전부 시도하는 것이라 지금의 "서버가 따로 보관하는 키"와 다르다. 일종의 키 스트레칭이다. Argon2는 선택 입력 비밀 값 K를 두고(RFC 9106 §3.1, "Secret value K is OPTIONAL") H₀에 섞으므로 pepper 자리로 쓸 수 있지만, RFC가 용도를 정하지는 않는다. K를 KDF에 직접 넣으면 키가 계산하는 서버 메모리에 올라와야 하므로, 63B-4의 "HSM 안" SHOULD를 따르려면 KDF 출력에 HSM 안에서 keyed hash를 한 번 더 거는 구성이 맞다(구성 판단은 추정).

해시를 아예 안 보내는 길: PAKE, 그리고 안 받는 길: FIDO

위의 모든 설계는 "패스워드가 서버에 도착한다"를 전제한다. TLS가 전송을 지키지만 서버 프로세스는 평문을 본다(로그에 찍힌 사고가 반복된다 — Facebook·GitHub·Twitter 2018~2019, 추정: 세부는 각 사 공지 참조). PAKE(SRP RFC 2945, OPAQUE)는 서버가 평문을 한 번도 못 보게 하는 프로토콜이고, 1Password는 로그인에, Apple은 iCloud 키체인 에스크로 복구(HSM이 SRP로 iCloud 보안 코드 검증, 10회 제한)에 SRP를 쓴다(각 사 보안 문서 기준). 그래도 서버에는 여전히 "패스워드에서 유도된 검증값"이 남아 오프라인 추측은 가능하다. 그것마저 없애는 것이 FIDO다: 서버에 공개키만 있으니 유출돼도 추측할 비밀이 없다. 이 페이지의 네 세대는 결국 "유출된 DB의 가치를 얼마나 깎나"의 역사이고, FIDO는 그 가치를 0으로 만든다.

흔한 오해

"암호화해서 저장하면 안전." 암호화는 키가 있으면 전부 되돌아간다. 저장 목적은 "되돌릴 수 없음"이므로 해시가 맞다. Adobe 2013이 이 차이의 비용을 보여줬다.
"SHA-256이면 충분히 강한 해시." 충돌 내성과 추측 비용은 다른 성질이다. SHA-256은 빠르게 설계된 함수라 공격자에게도 빠르다. 패스워드용은 일부러 느린 함수여야 한다.
"솔트는 비밀이어야 한다." 아니다. 솔트는 DB 행에 그대로 들어 있고 유출되어도 된다. 비밀로 두는 값은 따로 pepper라고 부른다.
"Argon2를 썼으니 패스워드 정책은 느슨해도 된다." KDF는 추측 한 번의 비용을 정하고, 정책은 공격자가 몇 번 안에 맞히는지를 정한다. 둘은 곱해진다. 상위 1,000개 안에 있는 패스워드는 어떤 KDF로도 못 지킨다.

내 연구와의 접점

오프라인 추측의 비용은 (KDF 1회 비용) × (정답까지의 추측 횟수)다. 이 페이지는 앞 항, 내 논문은 뒤 항이다. PentaPassBreaker가 top-5 안에 22.1%를 맞힌다는 것은 bcrypt cost 10 같은 느린 함수 뒤에서도 그 계정들은 5회 만에 열린다는 뜻이고, PSI가 낮은 지역·기관의 DB는 같은 KDF로 저장돼도 실질 비용이 자릿수로 낮다. 반대로 LastPass 2022처럼 "유출됐지만 KDF 뒤에 있는" 데이터의 실제 위험을 평가하려면 추측 모델의 성능 곡선이 필요하다 — 저장 기술 쪽에서 내 연구를 쓰는 자리가 거기다. Blocki 등의 모델을 쓰면 이 곱을 식으로 다룰 수 있다. 공격자는 추측의 한계 수익 pi·v가 한계 비용 k·(1 − λi−1)보다 작아지는 근처에서 멈추고, 그 pi를 정하는 것이 추측 모델이다. 논문은 모든 계정에 같은 분포를 가정하지만, 옛 패스워드를 아는 표적 공격자에게는 상위 순위의 pi가 훨씬 커서 같은 k에서 깨지는 비율이 커질 것이다추정. PSI 쪽 질문으로는, 지역·기관별 코퍼스에 Zipf 파라미터를 따로 피팅하면 같은 KDF 아래 합리적 공격자의 크랙 비율을 지역별로 예측할 수 있는가.
